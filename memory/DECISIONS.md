## D-001：以 Open-LLM-VTuber 1.2.1 为工程底座

- 日期：2026-08-21
- 状态：接受
- 决策：复用 FastAPI、WebSocket、ASR、TTS、Live2D、角色配置、历史和 MCP 框架。
- 原因：能最快建立可演示纵向闭环，同时把创新集中在宠物领域、记忆和共生世界。
- 影响：必须与上游代码边界保持清晰，并在计划窗口同步上游。

- 原因：保证从空目录克隆后具备完整可运行界面。
- 影响：同步上游前端需要人工记录来源并跑回归。

## D-003：当前 LLM 使用 StepFun 视觉模型

- 日期：2026-08-21
- 状态：接受
- 决策：通过 OpenAI 兼容适配器调用 `step-1o-turbo-vision`，支持文本和图片。
- 原因：满足宠物同时结合语音转写与摄像头画面进行回应的需求。

## D-004：宠物状态由 SQLite 和领域服务负责

- 日期：2026-08-21
- 状态：接受
- 决策：`PetStateService` 是业务规则入口，`PetStateRepository` 保存 `data/pet.db`；模型只能通过安全工具读取/改变状态。
- 原因：避免前端或 LLM 口述成为虚假状态，支持幂等、审计事件和离线时间变化。
- 影响：后续状态动作必须进入领域服务，并通过迁移维护数据库 schema。

## D-005：人格由 Persona System Prompt 驱动

- 日期：2026-08-21
- 状态：接受
- 决策：人格绑定 Prompt、音色、形象、口头禅和动作；当前正式人格为小太阳“小光”。
- 原因：保证文字、声音和视觉表达一致，并让真实状态/安全规则拥有系统级约束。
- 影响：未来四人格切换必须作为原子配置切换，不能只替换提示词。

## D-006：表情标签是控制协议，不是可见文本

- 日期：2026-08-22
- 状态：接受
- 决策：`[joy]`、`[neutral]` 等标签继续触发 Live2D，但在气泡、字幕、历史展示和 TTS 中隐藏。
- 原因：用户不应看到或听到内部动作标记。
- 影响：新增表情必须同时更新模型映射、Prompt 和回归测试。
- 证据：提交 `b5b6a0d`。

## D-007：合并过短句子以平滑 TTS

- 日期：2026-08-22
- 状态：接受
- 决策：相邻语音文本累计达到约 12 个有效字符再生成一个音频单元；长句保持流式输出。
- 原因：Edge TTS 每个 SentenceOutput 生成独立文件，短片段过多会造成播放间隙和文字跳动。
- 影响：极短首句可能等待下一个句子，但总体播放更连续；表情动作列表会合并保留。
- 证据：提交 `9ae4276`。

## D-008：项目上下文以版本化 memory 目录维护

- 日期：2026-08-22
- 状态：接受
- 决策：使用根级 `AGENTS.md` 自动入口和 `memory/` 结构化文件维护项目上下文。
- 原因：新窗口不会自然继承完整聊天历史；仓库文件可审查、可同步、可回滚。
- 影响：功能、架构、运行方式或优先级变化时必须同步更新对应 memory 文件；禁止保存密钥和隐私内容。

## D-009：宠物反应由领域事件和独立 WebSocket 驱动

- 日期：2026-08-22
- 状态：接受
- 决策：`PetStateService` 在动作成功时生成确定性的 `ReactionPlan`，并与状态差量写入同一个 SQLite 事件；浏览器通过 `/api/pet/events` 接收 `pet_state_changed` 和 `pet_reaction` schema v1。
- 原因：HTTP 状态按钮和独立 MCP 进程都会写同一个数据库，专用事件通道可以在不侵入现有对话 WebSocket 的前提下统一发现已提交动作，避免 LLM 或前端虚构反应。
- 影响：桌面单用户阶段按连接轮询 SQLite 事件序列；页面按 `event_id` 去重，重连通过 HTTP 获取快照。未来扩展高事件量时应替换为共享事件分发器，但保留公开 schema。

## D-010：反应渲染由服务端按真实 Live2D 资源解析

- 日期：2026-08-22
- 状态：接受
- 决策：新增 `src/open_llm_vtuber/pet_live2d.py`，读取 `model3.json` 与 `model_dict.json`，把 `ReactionPlan.animation` 解析为真实动作，找不到时回落到 `fallback_expression` 对应的真实表情，并在 `render` 中显式返回 `degraded`、`reason` 和 `missing_motion_asset`；`render` 作为 schema v1 的可选字段附加在喂食响应和 `pet_reaction` 消息上。
- 原因：模型资源是事实来源，前端不应猜测索引，领域层也不应认识美术资源。服务端解析可以用纯 Python 测试覆盖动作映射与降级路径，并让缺失的美术需求变成可查询的数据而不是口头 TODO。
- 影响：`mao_pro` 当前没有吃/玩/清洁/睡眠动作，喂食稳定走「开心表情 + 气泡 + 粒子 + 画布高亮」降级；补充动作素材后无需改前端即可自动启用。忽略 `render` 的旧客户端行为不变。

## D-011：反应音效使用 WebAudio 合成而非打包素材

- 日期：2026-08-22
- 状态：接受
- 决策：`feed_chime` 等音效由 `frontend/pet-status.js` 用 WebAudio 振荡器实时合成，提供面板静音开关（`localStorage: slai-pet-sound-muted`），浏览器自动播放策略拦截或缺少 WebAudio 时静默降级。
- 原因：避免引入第三方音频素材的许可与体积问题；音效属于反应表现，不能因为播放失败而影响状态写入、气泡或 TTS。
- 影响：音色由代码定义，替换为正式音源时只需替换播放实现；音效与 Edge TTS 使用独立音频通道，短促低音量，不覆盖语音。

## D-012：宠物动作走统一的幂等提交流水线

- 日期：2026-08-22
- 状态：接受
- 决策：`feed_pet`、`play_with_pet`、`clean_pet`、`put_pet_to_sleep` 共用 `PetStateService._commit_action`：同一 `request_id` 只写一次状态和事件，重复请求返回 `duplicate=True` 且不带 `ReactionPlan`；每个动作有独立事件类型（`PetFed`/`PetPlayed`/`PetCleaned`/`PetSlept`）和确定性反应计划。
- 原因：Phase B 之后动作会持续增加，重复实现幂等与差量逻辑必然产生分叉；统一流水线让「不能重复记账、不能虚构状态」成为结构保证而不是约定。
- 影响：新增动作只需要提供状态变更函数与 `ReactionPlan`；数值规则必须留在领域服务，前端与 Prompt 不得自行计算。

## D-013：睡眠是持久行为而不是一次性动画

- 日期：2026-08-22
- 状态：接受
- 决策：`put_pet_to_sleep` 把 `activity` 置为 `sleeping`，离线时间模型在该状态下改为恢复精力（`+6/h`）、缓慢回血回心情、饥饿增长减半，精力满后自动回到 `resting`。
- 原因：如果睡觉只是播放一次动画，关掉应用再回来宠物依然疲惫，状态就不再是真实的；恢复必须由服务端时间模型决定，而不是前端计时器。
- 影响：`_apply_elapsed_time` 现在按活动分支，后续新增「学习」「打工」等长期行为时应沿用同一模式；仍受 72 小时离线上限约束。

## D-014：头顶气泡由服务端投影，不劫持前端 bundle

- 日期：2026-08-22
- 状态：接受
- 决策：普通助手回复通过 `pet_speech_broadcaster` 在 `TTSTaskManager` 发送载荷的同一时刻广播 `pet_speech`，经 `/api/pet/events` 到达页面；不改压缩前端 bundle，不劫持 `window.WebSocket`，不靠 MutationObserver 猜测字幕 DOM。
- 原因：bundle 是构建产物，Chakra 生成的类名不稳定，DOM/WebSocket 劫持会在下次同步上游时静默失效；服务端投影用的是对话管线已经过滤好的同一份 `display_text`，能保证气泡、字幕、历史三者一致，并且可以用 Python 测试覆盖。
- 影响：气泡延迟受事件轮询间隔约束（默认 0.25 秒）；广播为进程内 fan-out，多进程部署时需要替换为共享通道，但公开消息 schema 不变。

## D-015：最近对话不是长期记忆

- 日期：2026-08-22
- 状态：接受
- 决策：侧边栏「最近对话」只显示 `PetSpeechBroadcaster` 的有界短期缓冲（默认 30 条、不落盘、不摘要），界面上明确标注；「共同记忆」保持空状态，直到真正的 `MemoryRecord`（来源、置信度、隐私级别、可编辑可删除）实现为止。
- 原因：把原始聊天记录直接摆进「共同记忆」会让用户以为宠物已经记住了，实际既不能解释来源也不能删除，属于对能力的虚假承诺。
- 影响：Phase G 实现长期记忆时，「共同记忆」面板换成真实记忆对象，「最近对话」保持为独立的显示缓冲，两者不得混用同一数据源。

## D-016：摄像头画中画镜像流，不接管应用自己的预览

- 日期：2026-08-22
- 状态：接受
- 决策：画中画由项目扩展 JS 自建容器，把已识别的摄像头 `MediaStream` 赋给自己的 `<video>`；不移动、不改写应用原生预览节点，也不给页面上任意 `video`/`canvas` 加通用样式。识别条件为「活跃摄像头轨道 + 无 `displaySurface` + 不在 `#live2d` 内 + 不覆盖整个舞台」。
- 原因：搬动 React 管理的 DOM 会在下一次渲染时被复原甚至报错；按类名匹配压缩产物同样不稳定。镜像同一个流不需要额外授权，也不会多开一次摄像头。
- 影响：应用自身的预览仍在原位；我们的画中画可以自由拖动、缩放和换形状。若上游改用非 `MediaStream` 的预览方式，需要更新识别条件而不是改样式。

## D-017：摄像头隐私边界写进代码而不是文档

- 日期：2026-08-22
- 状态：接受
- 决策：画中画模块只把流镜像到 video 元素——不做 canvas 绘制、不读像素、不上传、不持久化；停止入口两步确认后直接 `track.stop()`；「隐藏预览」只隐藏画面，指示灯与停止入口保持可见。后端侧以 `pet_speech` 的回归测试断言图片字段不会进入消息或最近对话缓冲。
- 原因：隐私承诺如果只写在文档里，后续任何一次改动都可能悄悄破坏它；用「不存在的能力」和「会失败的测试」来保证，比用约定可靠。
- 影响：将来若要做截图或作品生成，必须走独立的、有明确授权的受控工具层，不能复用这个预览模块。

## D-019：宠物的行为由优先级链决定，不由模型自由发挥

- 日期：2026-08-22
- 状态：接受
- 决策：`BehaviorPlanner` 按「用户即时互动（5 分钟内）> 状态告警（饥饿≥80 / 精力≤20 / 清洁≤25 / 心情≤20）> 确定性日程 > 待机」选择当前行为；第一版只允许休息、学习、玩耍三种可恢复行为，日程表固定且全天无空档。
- 原因：世界必须可解释、可复现、可测试。如果让 LLM 自己说「我在打工」，状态就又变回口述；固定优先级链让「为什么现在在做这件事」永远有确定答案，也让测试可以断言。
- 影响：新增行为要同时补日程槽、背景候选与交互清单；后续世界事件时间线、打工产出等应作为这条链的扩展，而不是绕过它。

## D-020：重启恢复事件，离线只给摘要

- 日期：2026-08-22
- 状态：接受
- 决策：世界事件持久化在 `pet_world_events`；重启后若事件仍在有效期且行为与原因未变，恢复同一个 `event_id` 与开始时间；离线超过 30 分钟时只生成一句按日程归纳的摘要，不补播事件或动画。
- 原因：真实的陪伴感来自「我不在的时候它也在过日子」，而不是回来后被一串补播动画轰炸；同时重启不该让宠物的下午从头开始。
- 影响：离线摘要目前由日程推导，等有了真实的世界事件时间线后应改为按已发生事件归纳。

## D-021：背景随时段与行为变化，且只用真实存在的素材

- 日期：2026-08-22
- 状态：接受
- 决策：背景由 `background_for(behavior, phase)` 决定，只提供磁盘上确实存在的 `backgrounds/*.jpeg`，缺失时降级为自绘渐变加时段色调；前端按 `img[src*="/bg/"]` 找到应用的背景容器，挂一个自有的双层交叉淡入层，不接管应用自己的 `<img>`，也不改它的 React 状态。
- 原因：`backgrounds/` 是 git-ignored 的本地素材，新克隆可能为空，硬编码文件名会变成裂图；而接管应用的背景元素会在它下次渲染时被覆盖。
- 影响：换素材只需替换映射表；若上游改变背景渲染方式（例如不再用 `/bg/` 的 `<img>`），需要更新定位方式而不是改样式。
